## Findings

### 1. FRAME. Which address population is actually probed?

`ANSWERED`. The documented population is the IPv4 space from 1.0.0.0 to 239.255.255.255 with reserved and special-use ranges excluded. IPv6 is documented as not currently supported. UDP scanning is documented as covering five ports only, which does not bear on a TCP/22 construct.

### 2. PORT COVERAGE. Is port 22 among the ports scanned?

`ANSWERED`. Port 22 is explicitly listed among the scanned TCP ports, in a documented list of more than one thousand curated ports. Mission 1.60 recorded port-22 inclusion as NOT established; it is established now, for the currently published list.

### 3. SAMPLING. Within the declared frame, is every address probed, or a sample of them?

`NOT_ANSWERED`. The documentation states that the IPv4 space is divided into large subnets and scanned in cycles, and that when one full scan completes the next begins immediately. It does not state whether every address inside a subnet is probed or a sample of it.

*Why this matters:* SAMPLING_IS_LOAD_BEARING, from Mission 1.59. A sampled population is not a census, and two apparatuses cannot be compared as one count unless both expose the same population definition. V1 implements no estimator to bridge them.

### 4. RETRIES. How many attempts does an address get before it is treated as not answering?

`PARTIALLY_ANSWERED`. The documentation states that for each service detected, the system makes only one request and saves the response. That describes the application-layer fetch against a service already found. It does not state the transport-layer probe behaviour: how many connection attempts an address receives on a port before it is treated as not answering.

*Why this matters:* The two are different measurements. A single-probe scan and a three-probe scan produce systematically different counts on a lossy path, and the difference would look like a disagreement between apparatuses rather than a difference in method.

### 5. FAILURE SEMANTICS. What does the absence of a record mean?

`NOT_ANSWERED`. No documentation retrieved distinguishes a host that was probed and did not answer, a host that was filtered, a host lost to packet loss, and a host not yet reached in the current cycle.

*Why this matters:* Mission 1.60 recorded the positive/negative asymmetry as a property of the construct: a successful identification is strong evidence, a failure to observe is ambiguous. The route therefore counts POSITIVE observed addresses only, and this question does not block that design — but a reviewer cannot bound the negative direction without it.

### 6. DUPLICATION. Can one address appear more than once for one port within one scan cycle?

`PARTIALLY_ANSWERED`. A record's unique identifier is documented as combining the uri and ip fields, so one host exposing several services yields several records. Whether one address-port pair can appear twice within one cycle is not stated.

*Why this matters:* The duplicate rule the construct needs is that a host observed several times inside the window counts once. That rule is expressible as a distinct count regardless of the answer, so this bounds the query rather than the construct.

### 7. DISTINCT-ADDRESS COUNTING. Is one record one host, or one host-port response?

`ANSWERED`. The ip field is documented as the address from which the response was received and is always present. Record identity combines uri and ip, so a record is one service response rather than one host.

*Consequence:* The construct's unit is distinct public IPv4 addresses, so the count must be a distinct count over the address field and never a record count. Recorded here because a row count would silently over-count multi-service hosts.

### 8. BANNER CAPTURE. Are the bytes the peer sent stored, and is anything truncated or normalised?

`PARTIALLY_ANSWERED`. The unparsed network response is documented as stored in a raw TCP field, and per-protocol banner fields are documented as the initial banner message returned by the server upon connection. No truncation policy, size cap or normalisation step is documented.

*Why this matters:* A3 passed on RAW_IDENTIFICATION_STRING, and the predicate is a literal prefix on the bytes the peer sent. A silent normalisation or a leading-whitespace trim would change what the prefix matches.
