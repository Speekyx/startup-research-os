## Findings

### SAMPLING — `UNKNOWN`

The data collection page states that the IPv4 space is divided into large subnets scanned in cycles, and that when one full scan completes the next begins immediately.

*Missing:* whether every address inside a subnet is probed, or a sample of them

*why load bearing:* SAMPLING_IS_LOAD_BEARING. A sampled population is not a census, and two apparatuses cannot be compared as one count unless both expose the same population definition. V1 implements no estimator to bridge them.

*silence is not an answer:* The documentation is silent. Silence is recorded as UNKNOWN and never mapped to NO_SAMPLING_ESTABLISHED.

### FRAME — `PARTIAL`

The eligible population is documented as IPv4 from 1.0.0.0 to 239.255.255.255 with reserved and special-use ranges excluded, and IPv6 as not currently supported.

*Missing:* the attempted frame: which addresses were actually scheduled and probed in a given cycle

*why load bearing:* The eligible frame is a declaration; the attempted frame is what a count is over. Nothing published lets the attempted frame be reconstructed or bounded.

*downgraded from answered:* Mission 1.61 recorded FRAME as ANSWERED. Section 6 separates ELIGIBLE_FRAME from ATTEMPTED_FRAME, and only the first is documented. Recording the split is the audit working rather than a reversal.

### RETRY — `UNKNOWN`

The FAQ states that for each service detected the system makes only one request and saves the response. The API reference documents client-side throttling and retry parameters in the CLI and SDK.

*Missing:* how many transport-layer connection attempts an address receives on a port before it is treated as not answering

*why load bearing:* A single-probe scan and a multi-probe scan produce systematically different counts on a lossy path, and the difference would look like a disagreement between apparatuses rather than a difference in method.

*the distinction that must not be lost:* The API reference's throttling and retry parameters govern the CLIENT retrying the API. They say nothing about the SCANNER retrying a probe. Reading the first as an answer to the second would be answering a measurement question with a transport-library setting.

### DUPLICATION — `PARTIAL`

*why load bearing:* It decides whether the distinct rule is a correction or a formality. It bounds the query rather than the construct, because a distinct count is expressible either way.

## Retrieval-surface facts established this mission

### dated index parameter — `ESTABLISHED`

The search request accepts a list of index labels, and the documented examples are calendar dates. The documentation states that if the parameter is not supplied the search runs against the latest publicly available internet scan data.

*consequence:* This is the verbatim confirmation of the Mission 1.61 bound. The admissible observation-addressable path is the explicit dated index; the default is the latest scan.

### count endpoint is an estimate — `ESTABLISHED`

The count endpoint returns an exact count below one thousand results, and above one thousand the count is documented as an ESTIMATE with an error margin not exceeding three per cent.

*why this is load bearing:* The construct is a count of distinct addresses over the public IPv4 space and will exceed one thousand by any plausible reading. A threshold comparison resting on that endpoint would be comparing a bound against an estimate whose error band could decide the direction, so a SUPPORTS or CONTRADICTS could be produced by the estimator rather than by the world.

*consequence:* A future route must not evaluate a threshold against the count endpoint. The documented alternative is the download endpoint, described as retrieving results without pagination limits, over which an exact distinct count is computable client-side.

*not a disqualification:* This bounds HOW the value must be obtained. It does not bound whether the apparatus can produce it.

### pagination bound — `ESTABLISHED`

The paginated search endpoint is documented as returning only the first ten thousand results; a separate download endpoint is documented as retrieving results without pagination limits.

*consequence:* Any exact distinct count over a large population must use the download route, which is a larger retrieval than a count and is therefore a larger governance and cost question for a later mission.
