## The pattern

**Five of eight classes have exactly ONE party positioned to produce the quantity, and one has none of its own — every other publisher of it is a distribution layer.**

That is Missions 1.46 and 1.57's law recurring across package registries, code forges, publication registries, procurement publishers and attention platforms — five domains it had not been tested in.

**The exception, and why.** The three classes with two independent producers are exactly the three whose quantity nobody is positioned to publish authoritatively: what services answer on the internet, what a web server returns for a defined request, and what a resolver receives for a defined query. Each must be established by asking, which is precisely the condition Mission 1.58 identified. The first of the three is the scanner class, which is parked for a different reason — it has two producers and no construct they can both witness, which is Mission 1.68's finding rather than a lineage problem.

## Lineage

## The class that came closest

**`Q1` Fixed-corpus HTTP / HTML observation.** It is the first class in this arc where two apparatuses are established first-party as independently PRODUCING observations of the same kind of thing, both publish dated artifacts, both publish which items they covered, and one stores the raw response with its HTTP headers.

*The one load-bearing question:* Whether a population can be frozen honestly when neither apparatus can be directed at the frozen corpus, so the joint population is the corpus intersected with two independently determined coverages.

*What makes it answerable:* Coverage is metadata rather than a measurement value, and both apparatuses publish it. A restriction rule could in principle be frozen before any value is retrieved.

*Why it was not selected anyway:* Because the question is open, and §35's preference for this class is a tie-break that may not push it through a failed gate.
