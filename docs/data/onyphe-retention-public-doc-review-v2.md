## The optimisation sentence

> We keep the last 30 days of data will all the fields and up-to 16KB of raw application responses. For data older than 30 days, we remove some fields as they are less useful, and we truncate data field to 4KB.

| operation | what |
| --- | --- |
| REMOVED | some fields, and the sentence does not name any of them |
| TRUNCATED | the data field, to 4KB |

**The sentence names the field it truncates and does not name the fields it removes. Mission 1.63 read it the same way and the reading is confirmed verbatim here.**

*Effect on the construct:* The predicate is a literal prefix of tens of bytes at the start of an identification string. A four-kilobyte truncation does not reach it. B3 stays `PASS`.

*The temptation refused:* Reading truncation as removal would reopen B3 and would be wrong. Reading truncation as harmless in general would also be wrong; it is harmless for THIS predicate because the predicate lives at the beginning of the field.

## Arguments available and refused

- **the archive would be useless without addresses** — An argument from what a sensible provider would do. It is not what this provider documents.
- **historical querying proves timestamps survive** — Historical querying proves that records are reachable in a past range. It does not prove which fields those records still carry, and the same sentence that grants seven months also says some fields are removed.
- **the fields are documented so they are retained** — The data model describes the schema. A schema says what a field means, never how long it lives.

**Silence is UNKNOWN. An unnamed removed field is not guessed in either direction, including when the favourable guess is the one a sensible provider would make true.**

*Why it is load-bearing:* A count over a past window needs each observation to be attributable to an address, a time and a vantage. If any of the three is dropped beyond thirty days, an older observation stops being locatable, and the window the construct names is longer than thirty days.
